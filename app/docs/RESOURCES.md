## 一、内容资源

| 资源 | 用途 | 正式获取方式 | 当前替代方案 | 阻塞 |
| --- | --- | --- | --- | --- |
| 试点城市地点数据 80—150 条 | 生成行程的候选池 | 人工整理 + 官方渠道核对 + 实地补充 | 20 条成都示例数据，字段按最终结构填写 | 否 |
| 地点图片 | 详情页、卡片视觉 | 自拍、官方授权、用户授权 | CSS 渐变 + 手绘剪影，不占带宽 | 否 |

| 营业时间 / 票价 / 预约规则 | 约束校验 | 景区官网、公众号、电话确认 | 三态模拟：已确认 / 待确认 / 固定休息 | 否 |
| 片区划分（4—6 个） | 排程的基本单位 | 按地理邻近人工划定 | 老城片、武侯片、东郊片、玉林片 | 否 |

| 城市介绍与推荐理由文案 | 内容质感 | 自行编辑 | 手写，控制在 40 字以内 | 否 |

**替代的质量标准**：字段结构必须与正式数据一致。宁可只有 20 条，也不要为了凑数改结构——结构一改，排程、校验、后台全部返工。

## 二、第三方服务

| 服务 | 用途 | 正式方案 | 当前替代方案 | 阻塞 |
| --- | --- | --- | --- | --- |
| 地图开放平台 | 地点检索、路径规划、导航跳转 | 高德 / 百度 / 腾讯位置服务，需企业认证 | 手绘抽象地图 + 直线距离 × 1.35 估算步行耗时，界面标注"估算" | 是（上线前） |
| 天气服务 | 出发前提醒、雨天替换建议 | 和风天气 / 彩云天气 | 不接入，页面不出现天气模块（不显示假数据） | 否 |
| 短信验证码 | 手机号登录 | 阿里云 / 腾讯云短信 | 游客模式 + 本地存储，无登录 | 否 |
| 对象存储 + CDN | 图片托管 | 阿里云 OSS / 腾讯云 COS | 无图片 | 否 |
| 大模型接口 | 自然语言改行程 | 任一家 API | 不做，纯规则引擎 | 否 |
| 推送服务 | 生成完成通知、出发提醒 | 厂商推送 / 个推 | 页面内轮询与提示 | 否 |

**地图是唯一真正的硬阻塞**。它同时卡住三件事：真实路径耗时、导航跳转、地图展示的合规性（审图号）。上线前必须解决，开发期可以用估算替代——但估算值必须在界面上显式标注，不能让用户以为是真实耗时。

## 四、开发环境

| 工具 | 用途 | 现状 | 替代方案 |
| --- | --- | --- | --- |
| Node.js 20+ | 前端构建 | ✅ 已装 v22.22.2 | — |
| npm | 包管理 | ✅ 已装 10.9.7 | — |
| Flutter SDK | 跨端 App 开发 | ❌ 未安装 | 先用 Vite + React 做移动端 Web，验证交互与排程 |
| JDK 17 | 构建 Android | ❌ 当前为 JDK 8，版本不足 | 同上 |
| Android SDK + 模拟器 | 真机调试 | ❌ 未安装 | 浏览器移动视图 + 手机浏览器直连 |
| Git | 版本管理 | ✅ 可用 | — |
| 代码编辑器 | 开发 | ✅ 已有 | — |

**为什么先用 Web**：Flutter + Android Studio + SDK 合计约 10 GB 安装量，且 JDK 需升级。当前阶段真正要验证的是"排程是否合理、交互是否顺手"，这两件事与框架无关。Web 版跑通后，用 Capacitor 可直接打包 Android，或按已验证的交互重写 Flutter——两条路都不浪费。

## 七、当前替代清单（本次开发实际使用）

| 正式资源 | 本次替代 | 替代的代价 |
| --- | --- | --- |
| 地图路径规划 | 直线距离 × 1.35，按 75m/min 估算步行 | 耗时不准，只用于验证排程逻辑 |
| 真实 POI 数据 | 20 条手写成都地点 | 覆盖不了真实城市，但结构一致 |
| 图片 | CSS 渐变 + SVG 剪影 | 视觉偏抽象，但加载快、无版权风险 |
| 登录体系 | 无登录，localStorage | 换设备丢数据 |
| 天气 | 不接入，模块隐藏 | 少一个卖点，但不给假数据 |
| 后端 | 纯前端，内存 + localStorage | 无法多端同步 |
| 地图 SDK | 手绘 SVG 示意图 | 不能导航，只能看相对位置 |

**替代的红线**：可以少功能，不能给错信息。估算的耗时必须标注"估算"，未知的营业时间必须显示"待确认"，不能用一个看起来合理的默认值把不确定性掩盖掉。
