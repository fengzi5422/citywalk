# 城市自由行 App 产品需求与规划设计

## 一、文档说明

### 1.1 目的与读者

本文档把"按城市推荐路线、生成日程、整合景点美食娱乐"这一初始想法，整理为可执行的产品需求，并给出产品规划设计方案。文档面向三类读者：产品与设计负责人据此确定范围与页面；研发负责人据此评估架构与工作量；内容运营负责人据此建立数据与维护流程。

文档分两层。第二章为需求整理，回答"到底要做什么、为什么这样切"；第三至十二章为规划方案，回答"怎么落地、按什么顺序做、做到什么程度算完成"。

### 1.2 产品定义

一句话定义：**为国内城市 1—5 天自由行游客，生成一份路线合理、可随时修改、旅行中能直接用、行程能长期保存的按天日程。**

产品不以"内容更多"取胜，而以"这份日程真的能照着走完"取胜。判断标准很直接：用户拿着手机出门，到了下一个时间点，知道下一站在哪、怎么去、要不要预约。

### 1.3 范围与假设

首版按以下假设规划，任何一条变化都会影响排期与架构：

| 维度 | 首版假设 | 变化后的影响 |
| --- | --- | --- |
| 目的地 | 国内城市，单城试点 | 出境游需重做地图、签证、汇率与合规 |
| 行程长度 | 1—5 天自由行 | 超过 7 天需引入"主题日"与中途休整 |
| 同行结构 | 1—4 人小团体 | 大团需车辆、餐饮桌位与分车调度 |
| 平台 | Android 内测优先 | 双端并行约增加四成前端工作量 |
| 团队 | 2 名全职开发 + 兼职内容 | 单人开发按每周 15—20 小时折算 |
| 商业模式 | 首版不接入交易 | 接入交易需资质、结算与售后体系 |

### 1.4 术语表

| 术语 | 含义 |
| --- | --- |
| 地点 | 可被安排的实体，包括景点、餐厅、场馆、休息点 |
| 活动 | 在特定日期与时段发生的项目，如展览、演出、夜游 |
| 场次 | 活动在某一天的具体开始时间与时长 |
| 片区 | 地理相邻、可步行或短程接驳的一组地点，是排程的基本单位 |
| 行程 | 用户的一次旅行计划，含若干天与每日若干项目 |
| 行程版本 | 行程的一次完整快照，用于回溯、分享与冲突处理 |
| 锚点 | 不可移动的时间约束，如到达、返程、预约场次 |
| 模板 | 人工维护的路线骨架，用于冷启动与质量兜底 |

## 二、需求整理：从想法到可执行需求

### 2.1 原始诉求拆解

初始想法包含四个诉求，本身是成立的，但只覆盖了"发现"与"建议"，没有覆盖"执行"。

| 原始诉求 | 用户真正想要的结果 | 首版对应能力 |
| --- | --- | --- |
| 按城市发现值得去的地方 | 不用翻十篇攻略就知道这座城有什么 | 城市页、主题分类、地点详情 |
| 推荐旅游路线 | 有一条被验证过、不用自己拼的走法 | 路线模板、一键复制为个人行程 |
| 安排每天的时间 | 几点出门、几点到、待多久、怎么去 | 排程引擎、时间线视图、交通估算 |
| 推荐景点美食娱乐 | 吃和玩都被安排在合适的位置 | 餐段插入、娱乐场次匹配、备选替换 |

四个诉求合起来，得到的是一份"建议"。用户真正需要的是"决定"：明天早上九点，我该出门去哪。这中间缺的是约束、可修改性与现场可用性。

### 2.2 四个必须补齐的缺口

**缺口一：旅行条件没有被采集。** 同样是两天，周六早上到和周六下午到，第一天能安排的内容差一个量级。住宿区域决定每天从哪出发、回哪结束；返程时间决定最后一天能放多少东西。没有这些条件，生成的日程只能算示意。

**缺口二：行程不能被修改。** 用户一定会改。改的原因有两类：一是偏好变化（不想去了），二是原计划不合理（太赶、太远、关门了）。产品如果没有编辑能力，第一次不合适就意味着弃用。

**缺口三：旅行中无法使用。** 攻略类产品的失效点集中在路上：找不到下一站、不知道还有多久、临时下雨。首版必须有一个"今天"页面，把"下一步做什么"压缩到一屏之内。

**缺口四：内容会过期。** 营业时间、门票、预约规则、场次都在变。没有来源、更新时间与复核机制的行程，会在某一天突然把用户送到关门的景区门口。这一条决定产品能否长期运营，而不是能否上线。

### 2.3 需求分层

把需求拆成三层，避免"功能列表"式的堆砌：

| 层级 | 内容 | 判断标准 |
| --- | --- | --- |
| 目标层 | 让用户完成一趟旅行，而不只是看到一份攻略 | 用户是否真的按计划走完 |
| 能力层 | 内容组织、条件采集、排程、编辑、随行、保存同步 | 每项能力是否可独立验收 |
| 功能层 | 具体页面与交互 | 是否服务于某项能力 |

目标层只有一句话：**把"做攻略"这件事从用户身上转移到系统身上，并且结果可被用户改动。**

### 2.4 首版边界

首版明确做：单城、1—5 天、Android、内容以自有与授权为主、排程以模板加规则为主、账号一种登录方式、分享只读快照。

首版明确不做，并在产品内不给出入口：机酒交易闭环、短视频社区、陌生人拼团、自动预约与代付、实时排队预测、出境游、跨城市联程。

边界之外的功能不是不重要，而是会同时拉高供给、运营与合规成本。首版只要把"一座城、一趟旅行"做扎实，后续扩展才有基础。

### 2.5 待验证假设

以下假设尚未验证，建议在第一周用访谈与小样本测试确认。假设错了，方案要改。

| 编号 | 假设 | 验证方式 | 若不成立 |
| --- | --- | --- | --- |
| H1 | 用户愿意花 3—5 分钟填写旅行条件 | 可用性测试，观察完成率 | 改为"先出稿、再补条件" |
| H2 | 用户更在意"少绕路"而非"多打卡" | 访谈排序题 | 调整排程权重，提高景点数量 |
| H3 | 行程被修改三次以内仍会被使用 | 内测行为数据 | 强化模板质量与默认值 |
| H4 | 用户愿意为准确信息等待 10—20 秒生成 | 生成耗时与放弃率 | 改为模板秒出 + 后台优化 |
| H5 | 单城 100 个左右地点足够支撑 3 天行程 | 覆盖率测算 | 扩充至 200 个或缩减天数 |

## 三、目标用户与核心使用场景

### 3.1 用户分层

首版聚焦三类核心用户，两类延展用户只做轻量支持。

| 层级 | 用户类型 | 核心诉求 | 首版策略 |
| --- | --- | --- | --- |
| 核心 | 首次到访者 | 不想漏掉重点，不想走冤枉路 | 经典模板 + 明确时间安排 |
| 核心 | 周末短途客 | 时间硬、只有 1—2 天 | 高密度片区组合，交通最省 |
| 核心 | 小团体同行者 | 要兼顾两个人偏好，要能一起看 | 偏好合并、只读分享 |
| 延展 | 亲子与长者同行 | 节奏慢、要休息、要少走路 | 通过节奏与步行强度选项支持 |
| 延展 | 本地探索者 | 同城周末找新鲜去处 | 第二版开放"附近"入口 |

### 3.2 用户画像

**画像一：效率优先的周末出行者。** 林晓，26 岁，互联网运营，和男友去成都玩两天。她的决策逻辑是"别浪费周末"：不想排队两小时，不想在两个景点之间坐一小时地铁。她会在高铁上订行程，需要十五分钟内拿到结果，并且能在路上改。她的放弃信号是"生成的安排明显不合理"，比如把两个相距很远的点排在一个下午。

**画像二：带家人出行的决策者。** 陈默，34 岁，带 6 岁孩子和父母去西安四天。他要的是"不出错"：中午要有正经吃饭的地方，下午要能回酒店休息，老人走不动时要能换掉下一站。他对信息准确性极敏感，一次"到了发现闭馆"就会让他不再使用。

**画像三：预算敏感的单人行。** 周雨，22 岁，大学生，一个人去重庆三天。她愿意接受推荐，但要有替代选项；她关心门票和餐饮花费，也关心"这个地方值不值得去"。她会因为一句"为什么推荐这里"而建立信任。

### 3.3 核心使用场景

**场景一：临时决定的周末出行。** 周四晚上十点，林晓决定周末去成都。她打开应用，选城市、选两天、选"轻松"，跳过住宿只填了预计区域，十五秒后拿到初稿。她把其中一晚的餐厅换成火锅，保存，分享给男友。

**场景二：出发前的最后确认。** 出发前一晚，陈默打开行程，看到系统提示"明天上午的博物馆需提前预约，当前未预约"，并附官方入口。他完成预约，把该场次标记为已预约，行程自动锁定该时段。系统同时提示第三天有雨，建议把户外段与室内段对调。

**场景三：旅行中的第一次改动。** 第一天上午十一点，排队比预期久。林晓点"跳过这一站"，系统保留已完成记录，从当前位置与当前时间重算剩余安排，给出两个替代点，并显示"下午的展馆将晚到 20 分钟，仍在最晚入场时间内"。她确认，生成新版本。

**场景四：天气突变。** 下午三点开始下雨。她点"剩余行程改为室内"，系统只调整未执行部分，把两小时户外段替换为附近室内展馆与咖啡馆，同时提示"晚餐预订时间不变"。

**场景五：回程后的沉淀。** 高铁上，周雨翻看已完成记录，标了三处喜欢的地点，把行程复制成"下次参考"，并导出只读链接发给朋友。她删掉了包含酒店信息的旧版本。

**场景六：弱网与断网。** 景区信号差，应用仍能打开已保存行程、查看备注、勾选完成；导航跳转到本机地图应用；恢复网络后草稿自动同步，若另一台设备已修改，提示比较而不是直接覆盖。

### 3.4 关键时刻与体验风险

用户对产品的判断集中在三个时刻，任何一个失败都会导致流失：

| 关键时刻 | 用户心理 | 设计应对 |
| --- | --- | --- |
| 第一次看到行程 | "这安排像人做的吗" | 每天两个主活动起步，交通时间显式可见 |
| 抵达当天下午 | "现在该干什么" | 首页直达"今天"，下一站与倒计时置顶 |
| 第一次需要改计划 | "改起来麻烦吗" | 一跳内完成替换，改动即时可见影响 |

体验风险按严重度排序：把闭馆地点排进去（致命）、交通时间明显失真（严重）、修改后地图与列表不一致（严重）、生成等待过长无反馈（中等）、分享泄露住宿信息（致命，属合规问题）。

### 3.5 非目标用户

跟团游与包车定制用户、商务差旅用户、以交易为目的的用户、需要无障碍设施精确承诺的用户，均不在首版服务范围。对最后一类，产品可以提供"步行强度"与"休息频率"选项，但不对电梯、坡道、无障碍卫生间做推断性描述。

## 四、核心功能清单与优先级

### 4.1 功能地图

功能按六个域组织：内容、生成、编辑、随行、账户、运营。每个域都有独立的验收标准，避免"整体做完了但没法验"。

### 4.2 P0 功能（首版必须）

| 模块 | 功能 | 完成标准 |
| --- | --- | --- |
| 城市内容 | 城市切换、分类浏览、搜索、筛选 | 能在三次点击内找到目标地点并加入行程 |
| 地点详情 | 地址、介绍、建议停留、开放信息、费用、预约入口 | 关键字段带来源与更新时间，未知项显式标注 |
| 路线模板 | 经典、轻松、美食等主题 | 可复制为个人行程并独立修改，不影响模板 |
| 行程创建 | 三步向导采集条件 | 必填项可跳过，跳过项在结果中标注假设 |
| 行程生成 | 按时间、偏好、住宿、锚点排程 | 不违反已知约束，排不下有原因说明 |
| 行程详情 | 时间线与地图同源展示 | 任一视图修改后另一视图立即一致 |
| 行程编辑 | 增、删、换序、换日、替换、锁定时长 | 每次修改触发交通与时间复检 |
| 冲突处理 | 识别闭馆、超时、赶不上预约 | 给出换序、换日、替换三类建议 |
| 今天页 | 下一站、倒计时、导航、完成、跳过 | 从打开到发起导航不超过两次点击 |
| 账号与保存 | 游客可用、一种登录、云同步 | 重启后数据仍在，冲突不静默覆盖 |
| 版本管理 | 自动版本、手动命名、回溯 | 可查看最近十个版本并恢复 |
| 收藏 | 按城市与类别收藏 | 可批量加入行程 |
| 分享 | 只读快照、有效期、撤销 | 服务端完成脱敏，撤销后链接立即失效 |
| 内容后台 | 地点维护、模板维护、上下架、报错处理 | 运营无需研发介入即可修正信息 |

### 4.3 P1 功能（核心稳定后）

| 功能 | 进入条件 | 价值 |
| --- | --- | --- |
| 天气联动调整 | 行程可行率稳定在阈值以上 | 降低现场改计划的成本 |
| 自然语言改行程 | 规则排程已稳定，AI 仅作入口 | 降低修改门槛 |
| 预约与出发提醒 | 账号与通知权限打通 | 减少"忘了预约"类失败 |
| 费用记录 | 行程结构稳定 | 支撑预算复盘 |
| 同行协作 | 已验证真实协作需求 | 提升分享转化 |
| 离线包 | 确认地图与图片授权范围 | 应对弱网与出境前场景 |

### 4.4 P2 功能（条件成熟后）

多城市联程、票务与商户合作、细分人群适配（亲子、无障碍）、UGC 攻略与评价、排队与拥挤预测。这些功能共同的前提是内容与运营能力跟得上，否则上线即负债。

### 4.5 明确不做

| 功能 | 不做的原因 |
| --- | --- |
| 机酒交易闭环 | 需要资质、结算、退改与客服体系 |
| 短视频社区 | 内容审核与推荐成本高，与核心价值无关 |
| 陌生人拼团 | 安全责任与匹配机制复杂 |
| 自动预约与代付 | 涉及第三方账号与资金，风险不可控 |
| 实时排队预测 | 缺乏可靠数据源，承诺即风险 |
| 出境游 | 地图、签证、汇率、合规全部需重建 |

### 4.6 依赖关键路径

首版真正的关键路径不是页面数量，而是三件事的先后：**内容可用 → 排程可信 → 编辑顺畅**。内容不齐，排程无从谈起；排程不可信，编辑只是在修补错误；编辑不顺畅，随行页没有意义。

因此开发顺序必须是：内容与数据结构 → 排程引擎 → 编辑与冲突 → 今天页与同步。倒过来做，会在联调阶段返工。

## 五、关键用户流程

### 5.1 主流程

**选择城市 → 填写条件 → 生成行程 → 调整确认 → 当天使用 → 保存与分享。**

六个步骤对应六个可测量节点：进入城市页、完成条件填写、生成成功、首次保存、旅行中使用今天页、产生分享或复用。每个节点都是转化漏斗的一环，缺一环就说明该环节设计有问题。

### 5.2 流程 A：首次创建行程

触发：用户在城市页点击"为我安排"。

主路径：

1. 第一步选日期或天数、选节奏（轻松 / 标准 / 紧凑）。
2. 第二步填到达时间、离开时间、到达站点、住宿区域、市内交通偏好。
3. 第三步选兴趣标签、预算区间、必去地点与已预约项目。
4. 点击生成，展示进度与预计耗时，可离开页面，完成后通知。
5. 进入结果页，顶部显示"本次安排采用的假设"，如"按市中心住宿估算，未含往返大交通"。
6. 用户可直接保存，或进入编辑。

分支与异常：

| 情况 | 处理 |
| --- | --- |
| 住宿未定 | 允许选择预计区域，结果页标注假设，后续可重算 |
| 日期未定 | 生成示意行程，标注"日期确定后需核对开放与场次" |
| 必去点排不进 | 结果页单列"未能安排"，给出原因与替代日期 |
| 生成失败 | 保留已填条件，提供"用模板快速生成"降级入口 |
| 重复提交 | 以幂等键去重，返回同一任务结果 |

### 5.3 流程 B：编辑与冲突处理

触发：用户在行程详情页拖动、删除或替换项目。

主路径：

1. 用户拖动某项目到下午。
2. 客户端本地即时预演，显示预计到达时间变化。
3. 服务端复检：开放时间、最晚入场、场次、交通耗时、返程余量。
4. 若冲突，弹出说明与三个选项：换序、换日、替换为附近同类地点。
5. 用户选择后生成新版本，版本号递增，旧版本保留。
6. 顶部出现"已保存"状态，弱网时显示"本地草稿待同步"。

设计要点：**冲突提示必须说明后果，而不是只报错。** "此安排将在 17:40 到达，该馆 17:00 停止入场"比"时间冲突"有用得多。

撤销：支持撤销上一步，保留最近二十步操作；跨天移动视为一步。

### 5.4 流程 C：旅行中的局部调整

触发：用户在"今天"页点击"跳过""换一站"或"剩余改为室内"。

主路径：

1. 系统读取当前时间、用户确认的位置、已完成与已跳过记录。
2. 锁定不可动项：已预约场次、返程余量、已完成项目。
3. 仅对未执行部分重排，已完成记录不改写。
4. 生成候选方案，展示新旧差异：总时长、总交通、费用变化。
5. 用户确认后写入新版本；取消则保留原计划。

关键约束：**不得自动改签或取消用户预约。** 若新方案赶不上预约，只提示"当前安排将错过 14:00 场次，请自行联系场馆处理"。

### 5.5 流程 D：保存、分享与复用

保存：自动保存 + 显式"保存为新版本"。自动保存每 30 秒或每次结构性修改触发一次，避免用户误以为已保存。

分享：生成只读快照，包含行程结构与推荐理由，不包含私人备注、票号、精确住宿坐标。快照有有效期，可随时撤销，撤销后链接立即失效。

复用：任意历史行程可"复制为新行程"，复制时提示"将按新日期重新核对开放与场次"，不直接沿用旧时间。

### 5.6 流程 E：异常与降级

| 异常 | 用户可见表现 | 系统行为 |
| --- | --- | --- |
| 地图服务超时 | 交通时间显示"待确认" | 用片区直线距离与默认速度估算并标注 |
| 天气接口不可用 | 不显示天气模块 | 隐藏而非显示错误值 |
| AI 服务超时 | 提示"本次使用规则生成" | 回落模板与规则引擎 |
| 保存失败 | 顶部提示"已存本地，待同步" | 草稿入本地队列，恢复后重试 |
| 多端冲突 | 弹窗对比两个版本 | 保留双方草稿，要求用户选择或合并 |
| 临时闭馆 | 行程项标红并给替代 | 触发局部重排建议，不自动替换 |

### 5.7 埋点与观测

必埋节点：城市页进入、条件填写完成率（分步骤）、生成请求与成功、生成时长、首次保存、编辑次数与类型、冲突触发与解决方式、今天页打开、导航点击、完成与跳过、分享生成与访问、内容报错提交。

指标口径要在开发前定死，否则内测阶段拿不到可用数据。

"今天"不占底部标签，而是行程内的置顶入口，并在旅行当天提升为行程页默认打开项。理由是它只在特定时间窗内高频，长期占位会稀释导航。

### 6.4 页面一：创建行程

分三步，每步一屏，可回退，可跳过非必填。

第一步：城市已选，填日期或天数、节奏。节奏用三段控件表示，配一句解释："轻松：每天两个主要活动，晚上可自由安排。"

第二步：到达与离开时间、站点、住宿区域、市内交通偏好。住宿未定时提供"我还没定"选项，选中后展示预计区域选择。

第三步：兴趣标签（最多选五个）、预算区间、必去地点、已预约项目。已预约项要求填日期与时间，系统据此锁定。

底部常驻主按钮"生成行程"，并显示"预计 15 秒"。生成过程展示三行进度文案，而非单调的转圈。

### 6.5 页面二：行程详情（核心页面）

信息层级自上而下：

1. **状态条**：城市、日期范围、保存状态、分享入口。
2. **日期切换**：第一天、第二天，横向滑动，显示每日主要活动数。
3. **当日概览**：主要活动数、交通总耗时、步行估算、费用区间、结束时间。
4. **视图切换**：时间线 / 地图。两者引用同一份数据。
5. **时间线**：按时间顺序排列行程卡，卡间显示交通段。
6. **底部操作**：添加地点、调整剩余、保存版本。

单张行程卡包含：预计到达时间、地点名、建议停留时长、一句推荐理由、预约状态、下一段交通方式与耗时、"换一个"入口。

设计红线：地图与时间线必须同源。用户改了列表顺序，地图上的连线若仍是旧路径，会直接摧毁信任。

### 6.6 页面三：今天

目标是在三十秒内回答"我现在该干什么"。

首屏只放四块内容：

1. **下一站卡片**：地点名、预计到达时间、距离与交通方式。
2. **倒计时**：若下一项是固定预约，显示"距 14:00 场次还有 1 小时 20 分"。
3. **三个动作**：导航、完成、跳过。次要动作"换一站"放在卡片内。
4. **今日剩余**：折叠列表，显示后续两到三项。

不放的内容：完整攻略文本、大段介绍、推荐理由长文。旅行中用户没有阅读耐心。

### 6.7 页面状态设计

每个核心页面必须定义六种状态，否则开发阶段会各自发挥：

| 状态 | 设计要求 |
| --- | --- |
| 空态 | 说明为什么空，给一个明确下一步动作 |
| 加载态 | 骨架屏，超过三秒显示文字进度 |
| 生成中 | 可离开，完成后通知，不阻塞其他操作 |
| 失败态 | 说明原因，给一个可执行的替代方案 |
| 离线态 | 顶部横条提示，已保存内容可读，标注"数据可能不是最新" |
| 冲突态 | 双版本对比，逐项选择，不做静默合并 |

### 6.8 体验原则

**一屏一决策。** 每个页面只让用户做一个主要决定，其余动作降级为次要入口。

**信息可追溯。** 任何关键字段（营业时间、票价、预约要求）都能看到来源与更新时间。

**未知要显式。** 缺失信息显示"待确认"，绝不用默认值填充成看似确定的事实。

**改动即时可见。** 任何调整在半秒内给出视觉反馈，长耗时操作先本地预演再服务端确认。

## 七、数据来源与更新策略

### 7.1 数据分层

数据分四层，权限与生命周期各不相同：

| 层级 | 内容 | 权限特征 | 生命周期 |
| --- | --- | --- | --- |
| L1 自有内容 | 城市介绍、片区划分、主题路线、推荐理由 | 完全可控，可长期保存 | 长期资产 |
| L2 授权内容 | 景区与场馆官方信息、授权图片 | 按授权范围使用 | 授权期内 |
| L3 接口数据 | 地图检索、路径规划、天气 | 按服务协议调用与缓存 | 短周期 |
| L4 用户贡献 | 报错、备注、评价 | 需授权与审核 | 依用户协议 |

分层的目的不是分类好看，而是回答一个具体问题：**这条数据能不能进数据库、能不能进离线包、能不能进分享快照、能不能发给模型。** 四层数据在这四个问题上的答案不同。

### 7.2 数据源矩阵

| 数据项 | 建议来源 | 使用方式 | 风险 |
| --- | --- | --- | --- |
| 城市与片区介绍 | 自行编辑、授权内容 | 入库，长期保存 | 人力成本 |
| 地点基础信息 | 地图开放平台检索 | 取必要字段，映射内部 ID | 字段不全、授权限制 |
| 营业时间与预约 | 官方渠道、合作方 | 人工核实后入库 | 更新不及时 |
| 交通耗时 | 地图路径规划接口 | 实时查询 + 短缓存 | 配额与费用 |
| 活动场次 | 场馆官方、票务合作 | 有接口用接口，无接口人工维护 | 场次变动频繁 |
| 天气 | 天气服务接口 | 按预报窗口展示 | 预报范围有限 |
| 图片 | 自拍、授权、用户授权 | 按许可展示并标注 | 版权风险 |

### 7.3 时效与更新策略

不同字段的更新频率差别很大，统一"每周更新"既不现实也不必要。建议按 TTL 分级：

| 字段 | TTL | 过期处理 |
| --- | --- | --- |
| 城市介绍、路线模板 | 90 天 | 标记待复核，仍展示 |
| 地点地址、类别、坐标 | 30 天 | 后台提醒复核 |
| 营业时间、最晚入场 | 7 天（重点场馆 3 天） | 降级为"待确认"，不参与硬约束判断 |
| 门票价格 | 14 天 | 显示"价格可能变动" |
| 活动场次 | 24 小时或实时 | 过期即从可排池移除 |
| 交通耗时 | 30 分钟（高峰/平峰分开缓存） | 重新查询，失败则标注估算 |
| 天气 | 按供应商窗口，出发前 72 小时加密刷新 | 范围外显示"出发前更新" |

过期不等于删除。过期数据的正确做法是降级展示并降低其在排程中的权重，而不是直接消失，否则用户会觉得信息莫名其妙不见了。

### 7.4 数据质量规则

**三态模型。** 每个关键字段只有三种状态：已确认、待核实、已关闭。禁止出现"空值当作无限制"的隐式假设。

**来源优先级。** 冲突时按 官方渠道 → 授权合作方 → 地图接口 → 用户报错 仲裁。用户报错必须二次核实才能覆盖官方信息。

**置信度门槛。** 关键字段置信度低于阈值的候选地点，不进入主推荐，只作为备选并标注"信息待确认"。

**一致性检查。** 排程前强制校验：坐标是否在城市范围内、开放时间是否与场次矛盾、停留时长是否超过营业窗口、地点是否被下架。

### 7.5 授权与使用边界

接口可以调用，不等于返回内容可以任意保存与再分发。接入前必须逐项确认五个问题：

| 问题 | 影响的设计决策 |
| --- | --- |
| 是否允许长期存储 | 决定能否建自有地点库 |
| 是否允许缓存 | 决定离线能力与响应速度 |
| 是否允许在分享页展示 | 决定分享快照可用字段 |
| 是否允许进入模型请求 | 决定 AI 功能的数据范围 |
| 是否要求展示来源标识 | 决定 UI 上的署名位置 |

在架构上对应四条硬规则：只存必要字段，不整包镜像第三方数据；内部地点 ID 与供应商 ID 分离，便于更换服务商；每个字段记录来源与更新时间；未获许可的数据不进入离线包、分享快照与模型请求。

### 7.6 内容冷启动

首版建议：一座城、四到六个相邻片区、80—150 个地点、8—12 条路线模板。

结构配比建议：景点约六成，餐饮约三成，娱乐与休息约一成。每个片区至少包含两个室内备选点，用于雨天替换；每个餐段在片区内至少有三个候选，形成"一主选两备选"。

数量不是目标，可维护性才是。100 个字段完整、每周可复核的地点，胜过 300 个信息残缺的地点。

### 7.7 内容运营流程

```text
线索收集 → 录入（含来源与截图） → 初审（字段完整性） → 上线
   ↑                                                    ↓
   └── 用户报错 ←── 定期复核（按 TTL） ←── 下线 / 修正在线
```

角色分工：内容编辑负责录入与初审，运营负责复核排期与报错闭环，产品负责模板质量抽检。报错响应目标为 24 小时内确认、72 小时内修正或标注。

### 7.8 内容健康度指标

| 指标 | 口径 | 目标 |
| --- | --- | --- |
| 字段完整率 | 关键字段齐全的地点占比 | ≥ 90% |
| 过期率 | 超出 TTL 未复核的字段占比 | ≤ 10% |
| 报错闭环时长 | 从提交到处理完成的中位数 | ≤ 72 小时 |
| 模板使用率 | 使用模板创建的行程占比 | ≥ 50% |
| 行程替换率 | 单份行程中地点被替换的比例 | 观察值，不设硬目标 |
| 冲突发现率 | 生成后被判定为不可行的项目占比 | ≤ 5% |

## 八、个性化推荐逻辑

### 8.1 四层结构

推荐系统拆成四层，各层职责不重叠：

| 层 | 输入 | 输出 | 失败影响 |
| --- | --- | --- | --- |
| 画像层 | 用户填写、行为、情境 | 偏好向量与约束 | 退化为通用偏好 |
| 召回层 | 城市候选池、片区 | 50—80 个候选 | 退化为模板地点 |
| 排序层 | 候选、偏好、时段 | 带分数的有序列表 | 退化为热度排序 |
| 排程层 | 有序候选、时间窗、锚点 | 按天行程 | 退化为模板行程 |

关键判断：**推荐层解决"去哪"，排程层解决"哪天几点去"。** 两者混在一起做，会导致推荐结果漂亮但排不进日程。

### 8.2 用户偏好模型

显式偏好：兴趣标签（历史、自然、美食、拍照、购物、演出、夜生活、亲子）取 0—3 强度；节奏三档；预算区间；步行接受度；饮食禁忌；交通偏好。

隐式偏好：浏览停留、收藏、加入行程、替换、跳过、完成后评分。隐式信号要衰减，十四天前的行为权重减半。

情境变量：同行结构（独自、情侣、朋友、带娃、带长辈）、季节与天气、是否首次到访。情境优先于长期偏好，带长辈时"轻松"应覆盖用户平时偏"紧凑"的设定。

### 8.3 候选召回

召回按片区进行，而不是全城平铺。理由很实际：跨片区组合会显著抬高交通成本，而用户的耐受度有限。

召回规则：先按城市与日期筛出可用地点（未下架、未关闭、信息置信度达标）；再按兴趣标签匹配度取前若干；再补足"必去""经典""餐段""室内备选"四类必需项；最后按片区聚合，保证每个片区都有足够候选。

每类地点设配额下限，避免召回的候选全是网红打卡点。例如餐饮至少覆盖三个价格带，景点至少包含一个免费或低价选项。

### 8.4 排序打分

首版采用可解释的线性加权，不做黑盒模型：

**总分 = 0.35×兴趣匹配 + 0.20×片区连贯 + 0.15×时段适配 + 0.10×预算适配 + 0.10×内容丰富度 + 0.10×口碑信号 − 0.10×拥挤风险**

| 因子 | 计算方式 | 说明 |
| --- | --- | --- |
| 兴趣匹配 | 标签命中强度归一化 | 冷启动主要依据 |
| 片区连贯 | 与前序地点的距离分档给分 | 同片区内优先 |
| 时段适配 | 类型与时段匹配（如夜游、餐段） | 避免把夜景排到上午 |
| 预算适配 | 费用落在区间内的比例 | 超预算降权 |
| 内容丰富度 | 字段完整度与图片质量 | 信息不全者降权 |
| 口碑信号 | 授权范围内的评分或人工评级 | 无可靠来源则置零 |
| 拥挤风险 | 节假日、热门度、时段 | 仅作轻微惩罚 |

权重需在真实数据上校准。冷启动阶段宁可权重简单、结果可解释，也不要上复杂模型导致无法定位问题。

### 8.5 排程算法

首版采用"锚点固定 + 片区聚类 + 贪心插入 + 局部改进"，不引入通用求解器。

步骤：

1. **固定锚点**：写入到达、离开、返程准备时间、已预约场次、用户锁定项。
2. **切分时间窗**：按天切出可用时段，扣除交通与缓冲。
3. **片区聚类**：把候选按地理邻近划为若干簇，形成"一天一片区"的初稿骨架。
4. **贪心插入**：在每个时间窗内按分数从高到低尝试插入，满足停留时长、交通耗时与缓冲要求。
5. **插入餐段**：午餐 11:30—13:30、晚餐 17:30—19:30 区间内选取就近餐厅，要求营业时间覆盖预计到店时段。
6. **插入娱乐**：仅有明确场次的活动按时段插入，冲突则放弃并记入未安排清单。
7. **局部改进**：用换序、换日、替换三种算子迭代若干轮，目标是最小化总交通时长、最大化兴趣总分、平衡每日强度。
8. **约束校验**：逐项复检开放时间、最晚入场、场次、返程余量、总预算。
9. **输出**：主方案、备选方案、未安排清单（附原因）、待确认事项。

复杂度控制：单日候选控制在 20 个以内，迭代轮数上限固定，保证生成在 15 秒内完成。超过时长的优化收益远小于用户等待成本。

### 8.6 节奏参数

"轻松"与"紧凑"必须对应具体参数，不能只是标签：

| 参数 | 轻松 | 标准 | 紧凑 |
| --- | --- | --- | --- |
| 每日主要活动 | 2 | 3 | 4 |
| 每日在外时长 | ≤ 8 小时 | ≤ 10 小时 | ≤ 12 小时 |
| 相邻项目最大交通 | 30 分钟 | 25 分钟 | 20 分钟 |
| 每日步行估算上限 | 6 公里 | 8 公里 | 12 公里 |
| 项目间缓冲 | 20 分钟 | 15 分钟 | 10 分钟 |
| 计划结束时间 | 20:00 | 21:00 | 22:00 |
| 晚间活动 | 可选 | 默认安排 | 默认安排 |

参数按地点类型修正：大型博物馆按 2.5—3 小时计，拍照点按 30—40 分钟计，不能统一取平均值。

### 8.7 可解释与可控

每条安排给一句理由，理由必须来自真实计算，不能套模板话术。四类可用理由：命中偏好（"你选了历史，这里评分最高"）、顺路（"距上一站步行 8 分钟"）、时段合适（"夜游段，19:00 后开放"）、硬约束（"已预约 14:00 场次"）。

未安排的项目必须给原因，归为六类：时间不足、开放冲突、距离过远、预算超限、偏好不匹配、信息待核实。原因是产品改进的输入，也是用户信任的来源。

### 8.8 反馈闭环与评估

行为闭环：替换与跳过作为负反馈，完成与收藏作为正反馈，更新兴趣权重；同类地点连续被跳过三次，自动降低该标签权重。

离线评估：可行率（生成后无需修正即可保存的比例）、冲突率、平均日交通时长、兴趣命中率、每日强度均衡度。

在线评估：首次保存率、生成到保存时长、编辑次数分布、今天页使用率、七日行程复用率。

注意一个反直觉现象：**修改率高不一定是坏事。** 用户愿意改，说明产品给了他表达偏好的空间。真正的问题是"改完仍然不合理"，而不是"改过"。

### 8.9 降级路径

| 失效环节 | 降级方案 | 用户可见提示 |
| --- | --- | --- |
| 画像缺失 | 使用城市通用偏好 | 不提示，结果页标注"通用推荐" |
| 排序服务异常 | 按人工评级与热度排序 | 无 |
| 地图接口失败 | 片区直线距离 × 系数估算 | 交通时间标"待确认" |
| 排程超时 | 返回模板行程 | "已为你生成基础方案，可继续调整" |
| 模型不可用 | 仅规则与模板 | 隐藏 AI 入口，不显示错误 |

降级的第一原则是**宁可少一个功能，不可给一个错误值**。零分钟交通、假营业时间、无来源票价，都会造成现场失败。

## 十、技术架构与关键设计

### 10.1 分层

客户端（Flutter 或 Kotlin）→ 接入层（鉴权、限流、日志）→ 领域模块（用户、内容、排程、行程、任务）→ 适配层（地图、天气、模型）→ 存储（PostgreSQL + 对象存储）。

首版保持单体后端，模块边界清晰即可。微服务、消息队列、向量库在真实压力出现前不引入。

### 10.2 核心数据模型

| 对象 | 关键字段 | 说明 |
| --- | --- | --- |
| 地点 | 内部 ID、供应商 ID、坐标、类别、片区、状态 | 双 ID 分离，便于更换数据源 |
| 开放规则 | 地点 ID、星期规则、日期例外、最晚入场 | 支持节假日例外 |
| 活动与场次 | 活动 ID、地点 ID、日期、起止、预约入口 | 场馆与活动分开建模 |
| 模板 | 主题、天数、适用条件、版本 | 模板版本化，避免改动影响历史行程 |
| 行程 | 所有者、起止、偏好快照、当前版本号 | 偏好快照保证可复现 |
| 行程项 | 顺序、日期、时间、停留、锁定、完成状态 | 与交通段分离 |
| 交通段 | 起终点、方式、耗时、来源、查询时间 | 记录来源与时间，便于判断时效 |
| 任务 | 类型、状态、幂等键、错误原因 | 支持重试与断点恢复 |
| 分享 | 版本号、有效期、撤销状态 | 快照式，不随原行程变化 |

两条必须从第一天做好的约定：内部 ID 与供应商 ID 分离；保存采用乐观锁版本检查，冲突时保留双方草稿。

### 10.3 异步任务

生成与重排耗时较长，采用"提交任务—轮询或推送—取结果"的模式。任务表记录状态、幂等键与错误原因，worker 可重启恢复。用户离开页面不中断任务，完成后通知。

### 10.4 离线与同步

本地 SQLite 保存：已保存行程、地点摘要（授权允许范围内）、用户备注、待同步草稿队列。同步采用"本地优先 + 服务端裁决"：本地改动立即生效并排队，联网后按版本号提交，冲突则拉取双版本对比。

### 10.5 降级矩阵

| 依赖 | 失败表现 | 降级策略 |
| --- | --- | --- |
| 地图路径 | 无耗时 | 估算 + 标注待确认 |
| 地图检索 | 无法搜索 | 使用自有地点库 |
| 天气 | 无预报 | 隐藏模块 |
| 模型 | 无响应 | 规则与模板 |
| 数据库主库 | 写入失败 | 只读模式 + 本地草稿 |
| 对象存储 | 图片加载失败 | 占位图 + 文字信息优先 |

### 10.6 成本控制

主要成本项：地图与天气调用、模型调用、图片存储与带宽、内容维护人力。控制手段：路径查询限制在候选集内而非全量两两组合；结果缓存并区分高峰平峰；生成任务合并去重；图片按需分辨率下发。

建议单独记录"每份可用行程的外部服务成本"，把失败重试也计入，否则会低估真实成本。

## 十二、验收标准

### 12.1 功能验收

按第四章 P0 清单逐项验收，每项需给出可复现的操作步骤与预期结果。验收用例与需求条目一一对应，不允许"看起来能用"式通过。

### 12.2 黄金场景

一条端到端场景必须完整跑通，才说明主要功能串起来了：

> 两名用户，两天行程。第一天 11:00 到站，第二天 17:00 离开；喜欢历史与美食，选择轻松节奏；第二天 10:00 有一个已预约的博物馆场次。第一天下午下雨，跳过一站并改为室内；途中在另一台设备上继续编辑并保存。

预期结果：生成方案满足到达与返程约束；跳过操作保留已完成记录；室内替换仅影响未执行部分；两台设备不出现静默覆盖；分享链接不含住宿信息。
